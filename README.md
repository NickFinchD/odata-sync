# odata-sync

Двусторонний обмен данными между 1С:Предприятие и внешними системами
через стандартный OData-интерфейс.

Написан, потому что типовой сценарий «выгрузить справочник из 1С, обработать
снаружи, залить обратно» каждый раз пишется заново — и каждый раз без
идемпотентности, из-за чего повторный запуск после сбоя плодит дубли.

## Что умеет

- Выгружать справочники и документы с автоматической постраничностью
- Загружать записи обратно: обновлять существующие, создавать недостающие
- Работать в режиме `--dry-run` — показать план, ничего не записывая
- Не падать целиком из-за одной проблемной записи

## Установка и запуск

```bash
pip install -r requirements.txt

export ODATA_URL="http://server/base/odata/standard.odata"
export ODATA_USER="Обменник"
export ODATA_PASSWORD="..."

# Выгрузить номенклатуру, только нужные реквизиты
python -m odata_sync.cli export Catalog_Номенклатура \
    --select Ref_Key Code Description --out nomenclature.json

# Загрузить обратно, сопоставляя по коду. Сначала — пробным прогоном
python -m odata_sync.cli import Catalog_Номенклатура \
    --file updated.json --key Code --dry-run
```

## Настройка на стороне 1С

OData не включён по умолчанию. Чтобы он заработал:

1. Конфигуратор → *Администрирование* → *Публикация на веб-сервере*
2. Отметить *Публиковать стандартный интерфейс OData*
3. Конфигуратор → *Общие* → *Http-сервисы* → состав стандартного интерфейса:
   добавить нужные справочники и документы
4. Завести отдельного пользователя для обмена с минимальными правами

## Принятые решения

**Идемпотентность через бизнес-ключ.**
Обмен падает посреди работы регулярно — сеть, перезапуск сервера, блокировка
объекта. Запись ищется по коду или артикулу и обновляется, если найдена.
Повторный запуск доводит дело до конца, а не создаёт вторую номенклатуру.

**Записи без ключа пропускаются, а не создаются.**
Без ключа невозможно гарантировать, что следующий запуск не сделает дубль.
Лучше пропустить и показать в отчёте, чем тихо засорить справочник.

**Апостроф в значении экранируется.**
`$filter` в OData — это строка, и значение вроде «Кабель О'Коннор» её ломает.
В худшем случае через незаэкранированное значение можно подмешать своё условие
в запрос, поэтому экранирование здесь — вопрос не удобства, а безопасности.

**Ошибка одной записи не останавливает обмен.**
Ошибки собираются в отчёт, остальные записи доезжают. Иначе выгрузка
на 5000 позиций падает на трёхсотой и всё приходится начинать заново.

**Реквизиты доступа только из окружения.**
Пароль от базы 1С не должен попадать ни в аргументы командной строки —
они видны в истории и в списке процессов, — ни тем более в репозиторий.

**Постраничность определяется по размеру ответа.**
1С не отдаёт общее число записей в удобном виде, поэтому признак конца —
страница короче размера окна. Это надёжнее, чем полагаться на `$count`,
который в 1С доступен не всегда.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

Живая база 1С для тестов не нужна: OData — это обычный HTTP, он замокан
через `respx`. Это принципиально — тесты, требующие развёрнутой 1С,
на практике не запускает никто.

Покрыты: постраничный обход, повторы на временных ошибках, создание
и обновление по ключу, пропуск записей без ключа, продолжение обмена
после ошибки, режим `--dry-run`, экранирование апострофа.
